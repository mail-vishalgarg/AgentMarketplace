1. Problem Statement — What Are We Building?

The single paragraph that defines the entire capstone project.

The Problem

Today, building an AI agent requires deep coding skills — you must write Python scripts, manage API keys manually, wire up tool integrations, and pray nothing goes wrong in production. There's no safety net if the AI decides to delete a database or post sensitive information to a public Slack channel.

Our Solution

Data Sense is a multi-tenant web platform where any employee (no coding required) can describe what they want an AI agent to do in plain English, and the platform automatically builds, tests, scores, and publishes that agent — with mandatory human approval for any risky actions. Think of it as an "App Store for AI Agents" inside your company.

The 6 Things a User Can Do (The Core Journey):

① Register a Tool Server

Paste a URL to a tool server (GitHub, Slack, Notion, etc.) and let the platform auto-discover its tools.

② Connect Credentials

Securely store your API token for each server — encrypted, never shown again.

③ Describe an Agent

Type in plain English what the agent should do. The platform builds its brain (config) through a 4-step guided conversation.

④ Test in Playground

Chat with the agent live. Risky actions (write/delete) pause and ask you for permission.

⑤ Publish to Marketplace

After scoring Grade B or above, submit for admin review. Approved agents enter the public Marketplace.

⑥ Install Someone Else's Agent

Browse the Marketplace, install an agent into your company, connect your own credentials, and run it.

5. Our Custom MCP Registry — Deep Dive + Code

We built our own MCP Registry from scratch. Here's exactly how it works and why.

What is MCP?

MCP (Model Context Protocol) is an open standard (created by Anthropic) that defines a common language for AI agents to talk to external tools. Think of it as "USB-C for AI tools" — one universal plug that fits GitHub, Slack, Notion, SQLite, or any service that builds an MCP server.

Why Build Our OWN Registry?

MCP itself is just a protocol (a set of rules), like how HTTP is a protocol. It doesn't come with a ready-made phone book of servers. In production, each company needs to track which MCP servers they have registered, what tools each server offers, and how risky each tool is. That phone book is our custom MCP Registry — stored in two PostgreSQL tables: mcp_servers and mcp_tools.

How a User Finds MCP Servers — Step by Step:

In Real-World Production:

  1. Your company's IT admin deploys MCP servers (e.g., github-mcp-server is an open-source npm package).
  2. Each deployed server runs at a known URL (e.g., https://mcp.yourcompany.com/github).
  3. You go to the "MCP Servers" tab in our platform, click "+ Register Server", and paste that URL.
  4. Official MCP registries exist (like github.com/modelcontextprotocol/servers) that list 100+ community-built servers.

In Our Demo Project:

  1. We ship 2 built-in mock MCP servers right inside our backend: /mock/github and /mock/slack.
  2. When you register http://localhost:8000/mock/github, our MCP Client connects to it and auto-discovers its 4 tools.
  3. The "fallback" in our client also handles Docker networking when the real HTTP call fails.
  4. To add SQLite, Notion, GitLab, etc. — you just deploy their community MCP server and paste the URL. Our Registry handles everything else.

The 3-Phase Registration Process (What Happens When You Click "Register"):

Phase 1: User Submits URL POST /api/mcp/servers with { name: "GitHub", url: "http://localhost:8000/mock/github" }
Phase 2: MCP Client Introspects Our client.py connects to the URL → calls GET /tools → receives the list of tools with names, descriptions, input schemas
Phase 3: Risk Classification Each tool's name + description is scanned with keyword matching → classified as READ, WRITE, or DESTRUCTIVE
Phase 4: Save to Database Server record → mcp_servers table. Each tool → mcp_tools table (with risk_level). Both scoped to tenant_id via RLS.

# backend/mcp_registry/client.py — Our custom MCP introspection client

import httpx

async def introspect_mcp_server(url: str, transport: str = 'sse') -> dict:
    """
    Connect to an MCP server and discover its tools.
    Returns {status, tools: [{name, description, input_schema, risk_level}]}
    """
    url_cleaned = url.strip().rstrip('/')

    # Step 1: Try real HTTP network introspection
    try:
        async with httpx.AsyncClient(timeout=4.0) as client:
            resp = await client.get(f"{url_cleaned}/tools")
            if resp.status_code == 200:
                data = resp.json()
                tools = []
                for tool in data.get('tools', []):
                    risk = classify_tool_risk(tool['name'], tool.get('description', ''))
                    tools.append({
                        'name':         tool['name'],
                        'description':  tool.get('description', ''),
                        'input_schema': tool.get('inputSchema', {}),
                        'risk_level':   risk           # ← auto-classified!
                    })
                return {'status': 'ok', 'tools': tools}
    except Exception:
        pass   # Server unreachable — fall through to fallback

    # Step 2: Fallback for built-in mock servers
    if 'github' in url.lower():
        return {
            'status': 'ok',
            'tools': [
                {'name': 'list_issues',  'risk_level': 'read',  ...},
                {'name': 'create_issue', 'risk_level': 'write', ...},
                {'name': 'close_issue',  'risk_level': 'write', ...},
            ]
        }
    elif 'slack' in url.lower():
        return {
            'status': 'ok',
            'tools': [
                {'name': 'list_channels', 'risk_level': 'read',  ...},
                {'name': 'post_message',  'risk_level': 'write', ...},
            ]
        }

    return {'status': 'down', 'tools': []}   # Unknown server

6. Automated Risk Classification — How READ/WRITE/DESTRUCTIVE is Decided

The platform never asks the user to label tool risk. It does it automatically using keyword matching.

The Actual Code:

# backend/mcp_registry/client.py → classify_tool_risk()

def classify_tool_risk(name: str, description: str) -> str:
    """Classify a tool's risk level based on its name and description."""

    # Keywords that mean "this tool DESTROYS data"
    destructive_keywords = ['delete', 'remove', 'drop', 'destroy', 'purge', 'truncate']

    # Keywords that mean "this tool CHANGES or CREATES data"
    write_keywords = ['create', 'post', 'send', 'write', 'update', 'put',
                      'patch', 'insert', 'push', 'publish', 'notify']

    combined = f"{name.lower()} {description.lower()}"

    # Check destructive FIRST (highest risk wins)
    if any(kw in combined for kw in destructive_keywords):
        return 'destructive'     # 🔴 MOST DANGEROUS
    if any(kw in combined for kw in write_keywords):
        return 'write'           # 🟠 RISKY — needs human approval
    return 'read'               # 🟢 SAFE — auto-executes

Example: How GitHub Tools Get Classified

Tool NameDescriptionKeyword MatchRisk Level
list_issues"List repository issues and PRs"No write/delete keywordsREAD
get_issue"Get a specific issue with comments"No write/delete keywordsREAD
create_issue"Create a new GitHub issue""create" matches writeWRITE
close_issue"Close a GitHub issue"No exact match → defaultsREAD
post_message"Post a message to Slack""post" matches writeWRITE
delete_repo"Delete an entire repository""delete" matches destructiveDESTRUCTIVE

Why This Matters

The risk level directly controls whether the AI agent can use the tool automatically or must stop and ask a human first. READ tools auto-execute (just reading data — no harm). WRITE and DESTRUCTIVE tools trigger an interrupt — the LangGraph execution freezes, saves state to PostgreSQL, and the UI shows an orange approval banner until a human clicks Approve or Reject.

7. Credential Vault — Fernet Symmetric Encryption

Where your API tokens go after you paste them — and why nobody can ever see them again.

The Metaphor: Bank Night-Deposit Box

When you deposit an envelope into a bank's night-deposit slot, it drops into a steel vault. You can't reach back in. The teller at the front desk can't see what's inside. Only the bank's master key (stored in a separate safe) can open it when a wire transfer must be authorized.

The Actual Code:

# backend/vault/credential_vault.py

from cryptography.fernet import Fernet
from config import settings

class CredentialVault:
    def __init__(self):
        # Master key loaded from .env file (never in code!)
        key = settings.APP_MASTER_ENCRYPTION_KEY.encode()
        self.fernet = Fernet(key)  # AES-128-CBC + HMAC-SHA256

    def encrypt(self, plaintext: str) -> str:
        # "xoxb-987654321-secret" → "gAAAAABnZ7k8W2qM9..."
        return self.fernet.encrypt(plaintext.encode()).decode()

    def decrypt(self, ciphertext: str) -> str:
        # Only called at the EXACT moment a tool needs the token
        return self.fernet.decrypt(ciphertext.encode()).decode()

# Single instance — created once at server startup
vault = CredentialVault()

1
Raw Ingress: You type your Slack token into the browser: xoxb-987654321-secret

The browser sends it over HTTPS to POST /api/connections.

2
Fernet Scramble: The Vault encrypts with the master key:

vault.encrypt("xoxb-987654321-secret") → "gAAAAABnZ7k8W2qM9..." (unreadable gibberish). Raw token wiped from RAM.

3
Zero-Leak Masking: When the browser loads the Connections table:

The API response replaces the secret with hardcoded dots: ••••••••. Neither hackers inspecting the network tab nor rogue employees can extract the real secret.

9. Database Bouncer — PostgreSQL Row-Level Security (RLS)

How we guarantee that Company A can NEVER see Company B's data — enforced at the database engine level.

The Metaphor: Hotel Elevator Keycard

In a luxury hotel, you step into the elevator and tap your keycard. You're on Floor 4. You press Floor 8, but the elevator refuses to move. Even if you guess codes on the keypad, the elevator mechanically ignores them. That's RLS — the database engine itself refuses to show rows belonging to another tenant.

How It Works (3 Steps for Every Request):

1
JWT decoded → extract tenant_id

FastAPI reads the login token from the request header → decodes it → gets tenant_id = "northwind-uuid".

2
Set session variable in PostgreSQL 
await session.execute(
    text("SELECT set_config('app.current_tenant_id', :tid, true)"),
    {"tid": str(tenant_id)}
)

This tells PostgreSQL: "For this entire database transaction, only show rows where tenant_id matches this UUID."

3
PostgreSQL enforces on EVERY query automatically 
-- This policy runs silently on every SELECT, INSERT, UPDATE, DELETE:
CREATE POLICY tenant_isolation ON agents
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid)
  WITH CHECK (tenant_id = current_setting('app.current_tenant_id')::uuid);

ALTER TABLE agents ENABLE ROW LEVEL SECURITY;
ALTER TABLE agents FORCE ROW LEVEL SECURITY;

Result: If Bob (Acme Corp) tries to load Alice's agent URL, PostgreSQL returns zero rows → API returns 404 Not Found. No code can bypass this — it's enforced at the engine level.

11. Human-in-the-Loop — Interrupt & Approval

The safety mechanism that makes sure the AI never takes a risky action without asking.

The Metaphor: Board Game with a Locked Backpack

A player walks around a board carrying a backpack (AgentState). At each room (node), they read notes from the backpack and add new notes. When they reach a room marked with a 🔴 red traffic light (a WRITE or DESTRUCTIVE tool), they must: ① Drop the backpack on the floor → ② Lock it with a combination lock (the checkpoint_id) → ③ Freeze. Even if the power goes out, the backpack is safe in the database. When the human clicks Approve, the lock opens and the player resumes.

The AgentState (The "Backpack" Data Structure):

class AgentState:
    messages:         list    # Chat history [User: "Triage issues", Bot: "Found 3 bugs"]
    current_node:     str     # Where on the board? "triager" or "reporter" or "done"
    approved_actions: list    # Tools the human approved ["slack.post_message"]
    rejected_actions: list    # Tools the human denied
    final_output:     str     # The final answer to show the user

What Happens at the Red Traffic Light:

Agent reaches "post_message" tool The tool's risk_level = "write" → approval_policy says "require_human"
LangGraph raises an Interrupt Execution halts → entire AgentState saved to PostgreSQL checkpoints table → server returns { status: "pending_approval" }
Browser shows Orange Banner "🟠 Agent wants to call slack.post_message. Message: 'Bug report digest for #engineering'." [Approve] [Reject]
Human clicks [Approve] POST /api/agents/{id}/runs/{run_id}/approve { approved: true } → LangGraph reloads checkpoint → resumes execution → tool fires → Slack message sent

12. Complete Request Lifecycle — What Happens When You Click "Send"

Every byte traced from your browser click to the Slack message and back.

1
React Frontend: You type "Triage open issues" and click Send.

Axios sends: POST /api/agents/a1/invoke with body { message: "Triage open issues" } and header Authorization: Bearer <JWT>.

2
FastAPI Gateway: Authentication + Tenant Context

Decodes JWT → reads tenant_id = Northwind Labs → runs SET LOCAL app.current_tenant_id = '...' → loads agent config from DB (RLS-scoped).

3
LangGraph Runtime: Builds the graph and starts the Supervisor.

Reads AgentConfig JSON → creates StateGraph → Supervisor routes to Issue Triager node → Triager calls GET /mock/github/tools/call/list_issues → returns 3 open bugs.

4
The Pause Gate: Supervisor routes to Digest Reporter → notices slack.post_message

Runtime halts! Saves state to checkpoints table. Returns to React: { status: "pending_approval", tool: "slack.post_message" }.

5
Browser Display: React shows the Orange Approval Banner.

The chat displays: "🟠 Agent wants to post to Slack. Allow?" with green [Approve] and red [Reject] buttons.

6
Human Approval: You click [Approve].

Axios sends POST /api/agents/a1/runs/{id}/approve { approved: true } → LangGraph reloads checkpoint → decrypts Slack token from Vault → executes post_message → marks run as SUCCESS → returns response to chat.

13. Marketplace & Cross-Tenant Installation

How an agent travels from one company to another — safely.

The Metaphor: An App Store Download

When you download an app from the App Store, you don't get Apple's internal server credentials or employee data. You get a clean, sanitized package. Similarly, our Marketplace strips ALL company-specific data before publishing.

The Sanitization Pipeline (What Gets Stripped):

# backend/marketplace/sanitizer.py — strips company-specific data

def sanitize_for_marketplace(agent, tenant_name):
    config_str = json.dumps(config)

    # Remove company name → replace with [Company]
    config_str = config_str.replace(tenant_name, '[Company]')

    # Remove emails → [REDACTED_EMAIL]
    config_str = re.sub(r'[\w.+-]+@[\w-]+\.[\w.-]+', '[REDACTED_EMAIL]', config_str)

    # Remove API keys (OpenAI, Slack, GitHub tokens)
    config_str = re.sub(r'sk-[a-zA-Z0-9_-]{16,}', '[REDACTED_KEY]', config_str)
    config_str = re.sub(r'xoxb-[a-zA-Z0-9_-]+',   '[REDACTED_TOKEN]', config_str)
    config_str = re.sub(r'ghp_[a-zA-Z0-9_-]+',     '[REDACTED_TOKEN]', config_str)

    # Remove internal URLs
    config_str = re.sub(r'https?://(?:internal|corp)[\w./-]*', '[REDACTED_URL]', config_str)

    return sanitized_config   # Clean, safe to publish

Installation Flow (What Happens When Someone Clicks "Install"):

Bob (Acme Corp) browses Marketplace GET /api/marketplace → sees "Issue Digest Bot" by Northwind Labs, Grade A, 12 installs
Clicks "Install" POST /api/marketplace/{listing_id}/install → copies config_template into Bob's tenant → creates new Agent in Acme Corp's agents table
Missing Connections Detected Agent requires GitHub + Slack servers, but Bob's Acme Corp doesn't have Slack connected yet → UI prompts Bob to connect credentials
Bob runs the agent in his own Playground Agent uses Bob's credentials, runs in Bob's tenant, data isolated via RLS — Northwind Labs never sees Bob's data
